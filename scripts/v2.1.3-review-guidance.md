`CHANGELOG.md:22` names `docs/release-runbook.md`, but `.gitignore:28` is `/docs/` and the file is not tracked. A clean checkout or release source archive therefore cannot supply the promised document.

**Guidance:** place the runbook in an intentionally tracked documentation location, or add a narrow ignore exception. Verify its presence in the commit/archive before claiming this gap closed. Avoid force-adding unrelated ignored local documentation. Correct the release notes if shipping it in a later patch.

### 2. Correct the local runbook's validation commands before publication

The local-only document has additional problems:

- Line 19 pipes `go test ...` through `grep`. A clean run produces no grep matches and exit 1; a matching failure line yields exit 0. Without explicit exit capture, build failures may also be hidden. Use the existing JSON gate pattern, preserving the test process exit code and checking skips separately.
- Lines 35–38 assume `/home/Sniffer/antifox` and a pre-existing `backups/` directory. Unquoted `<version>` is shell syntax, not a safe executable placeholder. Use clearly assigned variables and validated directories in examples.
- `pg_restore --list` is an archive listing, not a successful restore. Keep it as a preliminary check, but require a restore into a disposable database and post-restore validation as evidence.
- Lines 111–113 assert rollback compatibility because migrations are additive. Schema additions alone do not prove compatibility of changed tool definitions, behavior or data. Rehearse the previous image against the upgraded disposable copy before making that claim.

These are documentation/process corrections; do not test backup/restore examples against production during this review.

### 4. Keep historical cleanup separate from new input validation

The six missing-task references remain. Determine provenance before removing or assigning them; preserve a rollback record. Do not mark the live data-integrity gap closed merely because new input is validated.

**Further limitation:** validation is a pre-write lookup, not a relational invariant. `db/tasks.go:DeleteTask` deletes tasks/explorations while leaving global assets untouched; `assets.task_ids` is still an array without an FK. A later task deletion or a concurrent deletion can leave references even after ingestion validation succeeds. Define whether these IDs are historical provenance or active associations. If active, test deletion cleanup and transaction/race behavior. This is a broader follow-up, not evidence that the new invalid-input checks fail.

## Claims and tests that still need qualification

### Cancellation causes are named in text, but not separately persisted

`db.Activity.Outcome` distinguishes completed/cancelled/failed/budget states, while `agent/cancelcause.go` renders the cause into summary text. This meets the immediate UI issue. For cause-based metrics or localized messages, consider a stable optional `cancel_cause` code instead of parsing prose. Existing historical rows remain nullable and are not automatically reclassified.

The tests exercise cause propagation and result storage; they do not prove every pause/stop/shutdown HTTP/UI sequence or SIGKILL termination produces a final row. Do not promise that an abruptly killed process can always persist its cancellation.

### Output preservation is conditional

`engine/harness/tools.go` reports excess non-text blocks but does not serialize them to spill storage; only omitted text is passed to `tool.Capture`. If spill storage is unavailable, text uses head/tail truncation. Therefore the changelog's claim that "anything over the budget is saved" is too broad. Describe text spill as conditional and non-text omission explicitly.

The text budget includes some extra notice overhead; tests allow that slack. Eight image blocks can still have large payloads. Treat image byte budgeting as a separate follow-up requirement rather than claiming an absolute whole-result memory cap.

### Secret handoff protects startup availability with a documented tradeoff

The new nonblocking write removes the reviewed wait-before-reader hazard. Oversized/failed handoffs intentionally continue with secrets in the initial process environment and log a warning, as stated in the implementation. Runtime environment scrubbing still runs later. Document the distinction between startup availability and guaranteed initial-environment secrecy; keep warnings free of secret values.

### Test coverage versus upgrade evidence

The exact-release Go test and race results are now verified on the production PostgreSQL major version. Hosted frontend build success is also confirmed. Still not demonstrated here: a restored-production-data migration rehearsal, browser-level cancellation rendering, a final-image startup test across supported operating systems, or a complete vulnerability/dependency audit. Frontend lint is not an explicit release step.
