# AntiFox v2.1.2: release gaps and improvement plan

Date: 2026-11-14

## Decision

**Keep the running release; do not roll it back solely for the observed chat interruption. Do not give unconditional release approval yet.** Prioritize data-preserving migrations, standalone task-reference validation, accurate cancellation reporting, and mandatory release gates. Preserve the security controls.

This is a bounded continuation review of release correctness, data integrity, lifecycle observability, startup and packaging. It is not a full-repository security audit, an assessment of exploit effectiveness, or a guarantee of capability parity/zero downtime. No application source or production records were modified for this review.

## Findings and remediation acceptance criteria

Priority indicates recommended work order, not a CVSS score. Static findings do not establish that a particular production incident occurred.

### D1 — Migration can misclassify customized settings (P1)

**Evidence:** `server/orchestration.go:620–625`:

```go
isStock := cur.Description == "" ||
    cur.Description == seed.Desc ||
    strings.HasPrefix(cur.Description, "Search for asset bank") ||
    strings.HasPrefix(cur.Description, "Search the asset store") ||
    strings.HasPrefix(cur.Description, "搜索资产库")
if cur.Description != seed.Desc && isStock {
```

The migration rebuilds the schema from defaults and copies only existing `default` values (`:626–645`, `sm["default"] = def`). `RefreshToolDefaults` replaces description/schema (`db/tools.go:94`). A customized description beginning with a recognized prefix is therefore eligible for replacement; custom parameter descriptions and constraints are not carried over.

**Alternative checked:** arbitrary custom descriptions are preserved; the defect is specifically prefix-retaining customization or schema-only customization with old stock wording. The test's `"CUSTOM USER LIST ASSETS"` fixture (`server/migration_regression_test.go:155`) does not cover those cases.

**Status:** statically established edge case; no pre-upgrade production snapshot available to prove any live customization loss.

**Acceptance:** use explicit version/provenance or exact known-default comparisons, preserve operator-owned fields, and test schema-only edits, prefixed descriptions, defaults, constraints, disabled state and bindings. Do not erase customization to force an upgrade.

### D2 — Migration completion can be recorded without a schema upgrade (P1)

**Evidence:** `server/orchestration.go:625`, `if cur.Description != seed.Desc && isStock`, and `:651`, `_ = s.m.pg.SetSetting(flag, "true")`.

A current description with a stale schema skips the refresh and still gets a completion flag. Description equality is not schema compatibility.

**Alternative checked:** a fresh database already has the current schema, so that case is fine. The problem is a partially upgraded or edited database. The existing test uses an old description (`server/migration_regression_test.go:118`) and cannot establish this case works.

**Status:** statically established; not currently observed on the live `list_assets` row, which has `q`, `dsl`, `company_id` and `task_id` and a planner binding.

**Acceptance:** verify schema postconditions independently of description text; record completion only after success or an explicit preserved-custom disposition. Test restart/idempotency, incomplete schemas and failed writes. Handle migration-marker persistence errors rather than discarding them.

### D3 — Standalone task references remain unchecked (P2)

**Evidence:** `agent/tools_insert.go:193–201`:

```go
taskID := t.taskID
// bound-task branch omitted
} else if a.TaskID > 0 {
    taskID = a.TaskID
}
```

`db/assets.go:280–281` turns a positive task ID into an array value without a task lookup: `taskIDs = fmt.Sprintf("{%d}", req.TaskID)`. The bound-task override fix is useful, but the standalone path still accepts nonexistent IDs.

**Test mismatch:** `agent/tools_regression_test.go:128–145` deliberately uses standalone ID `88888` and expects it to be persisted. A passing test currently preserves the behavior that the earlier remediation proposal intended to eliminate.

**Status:** source and existing test establish the gap. The live orphan query found missing task `75` on six assets: `132,134,135,138,139,141`. Those associations predate v2.1.2; their presence does not prove new-release corruption or that all orphans share this cause.

**Acceptance:** reject nonexistent explicit task references before writing; distinguish an intentionally unassigned asset from an invalid reference. Test valid, missing, zero, negative and conflicting references. For historical records, generate a reviewed dry-run repair plan, retain a backup and verify provenance before reassignment.

### D4 — Cancellation message hides the actual cause (P2, pre-existing)

**Evidence:** `agent/capture.go:125–130` maps both `ReasonAbortedTools` and `ReasonAbortedStreaming` to:

> (Operation interrupted: Task suspended / Termination / As a result of restart; not completed)

`agent/capture.go:140` sets `IsError: ev.Terminal.Err != nil`. Task chat cancels the previous run on a new message (`server/server.go:2162–2163`). Live sequence `7915` (user message), `7916` (tool interrupted), `7918` (generic result), followed by new activity supports that cause for the observed turn. The cancellation behavior predates v2.1.2.

**Alternative checked:** actual restarts and operator stops can also cause cancellation; the generic string alone cannot distinguish them. Do not infer a restart from this text.

**Acceptance:** persist structured outcome and cancellation cause; distinguish replaced-by-message, operator stop, deadline and shutdown, with unknown as a valid fallback. Display cancelled separately from failed, retain real errors, and add deterministic lifecycle tests. Changing to queued-message behavior is a separate product decision, not required for this fix.

### D5 — Release publication lacks an explicit Go test/vet dependency (P1, release gate)

**Evidence:** at tag `v2.1.2`, the workflow inventory consists of `.github/workflows/release.yml` and `publish-package.yml`. In `release.yml`, binary compilation depends only on frontend (`:34`, `needs: frontend`), and publication depends only on binaries (`:94,:130`, `needs: binaries`). The build step runs `go build` (`:64`); neither checked workflow runs `go test` or `go vet`.

**Alternative checked:** the frontend build is a real gate, and external branch policy may impose other checks. Hosted rules/history were not inspected. Therefore this finding concerns the checked-in publication dependency graph, not a claim that nobody tested the release.

**Acceptance:** gate publication on vet, database-backed tests with fail-on-skip/configuration checks, and platform-correct UI validation. Test against the production PostgreSQL major version and pgvector. Publish machine-readable test results and the tested source revision; ensure manual publishing follows the same gates.

### D6 — Docker architecture comments exceed the configured publication (P3, documentation/configuration drift)

**Evidence:** `.github/workflows/release.yml:127` says `Push multi-architecture images`, but `:162` specifies `platforms: linux/amd64`. Its binary matrix separately includes Linux arm64 (`:40`). The manual publication workflow also builds an amd64 image.

**Alternative checked:** arm64 binary availability is not equivalent to an arm64 container image. amd64-only publication may be deliberate; it is not evidence that current amd64 production is broken.

**Acceptance:** explicitly document the supported image platform and separate it from binary-platform support. If additional image platforms are promised, require platform-specific startup and dependency evidence before making that promise.

## Risks requiring additional validation (not confirmed production defects)

### R1 — Result-size limit is per text block, not aggregate

**Evidence:** `engine/harness/tools.go:116–123`: `for i, b := range res.Content` and `res.Content[i].Text = tool.CaptureOnce(tc, b.Text)`. The higher-level comment at `:84–87` claims every output is bounded so no tool can flood the context. `capoutput_test.go:13–23` exercises one large block; `:35–42` exercises one small text block plus an image.

**Conclusion:** the implementation limits individual text blocks; it does not establish a total result budget. Many individually small blocks can exceed the intended aggregate size. Whether this occurs in real integrations or is limited elsewhere was not validated; no memory-exhaustion test was run.

**Improvement:** define a total text-result budget plus a separate non-text budget. Add bounded synthetic multi-block tests, preserve ordering, and clearly report omitted/persisted content. Avoid falsely claiming an aggregate guarantee from a single-block test.

### R2 — Startup secret handoff assumes sufficient pipe capacity

**Evidence:** `cmd/antifox/secrets_linux.go:21–23` claims a 32 KiB payload stays below pipe capacity; `:67` calls `w.Write(data)` before `:89` executes the process that reads the pipe. Existing `secrets_linux_test.go:36–43` uses short credentials; its `cmd.CombinedOutput()` at `:43` has no explicit subprocess deadline.

**Conclusion:** on systems where the accepted payload exceeds available pipe capacity, the blocking write could wait before a reader exists. This review measured a 65,536-byte default pipe on WSL, so it did **not** reproduce a failure. The live server is running. Do not report this as its current outage cause.

**Improvement:** test the complete handoff with bounded deadlines and varying payload sizes/capacity; use a transfer design that does not assume a fixed pipe buffer. Keep secrets out of logs and preserve the existing credential protection.

## Improvements to working behavior

### E1 — Make upgrades auditable and reversible

**Current evidence:** `docker-compose.yml:3–7` changes the PostgreSQL image and instructs `REINDEX DATABASE` after a musl-to-glibc switch. Live metadata reports matching collation versions and installed vector; those checks do not establish that every required index was rebuilt.

**Proposal:** a release runbook should record database backup/restore verification, source and image digests, migration outcomes, collation/index checks and rollback compatibility. Validate on a restored disposable production-version database before touching live state. Benefit: operator confidence and repeatability. Effort: medium. Risk: treating a checklist as a substitute for actual restore evidence.

### E2 — Publish compatibility changes alongside fixes

**Current evidence:** `guard/guard.go:140–143`, `if !allowAsk { return g.block(...) }`; `server/env_scrub.go:14,25–28` removes named startup credentials from inherited environments. These are deliberate protections, not established defects.

**Proposal:** document changed approval behavior, child-process credentials, first-run setup and stored-key endpoint checks. Validate ordinary approved integrations explicitly. Benefit: fewer surprises. Effort: small. Do not solve compatibility complaints by disabling security controls.

### E3 — Describe verification labels precisely

**Current evidence:** `server/finding_verification.go:74–87` checks declared proof level and quote presence; `:129–133` matches normalized quoted text using `strings.Contains`. This performs evidence consistency checking, not independent semantic proof of the finding.

**Proposal:** explain the label's criteria and limits in the UI/help and retain human disposition separately. Benefit: avoids overconfidence without removing evidence checking. Effort: small. Do not relabel historical data as verified solely to improve counts.

## Test plan and gaps for Gemini

| Area | Required acceptance evidence |
| --- | --- |
| Migrations | Stock, prefixed-custom, schema-only-custom, current-description/stale-schema, repeat startup, failed update and failed marker persistence |
| Task references | Valid and invalid standalone references; bound context cannot be overridden; rejected request produces no partial writes |
| Historical cleanup | Before/after counts, approved mapping and rollback script; no blanket reassignment |
| Cancellation | New message, stop, timeout, shutdown, genuine failure; correct persisted outcome and UI state |
| Output budgeting | Multiple small blocks, multiple large blocks, mixed content, UTF-8 boundaries, unavailable spill storage |
| Secret handoff | Bounded subprocess timeouts; payload boundaries; restore failure; secrets absent from logs and initial environment |
| Release gate | Clean install, UI build/lint/typecheck, backend vet/tests/race, explicit database execution, artifact revision binding |
| Database upgrade | PostgreSQL 16 + pgvector, restored data, collation/index plan and rollback compatibility |

The existing tests are useful but incomplete. Do not change assertions just to obtain green results; encode the intended contract first. Run only against disposable databases. Some tests alter global settings and active prompt versions (`server/migration_regression_test.go:104–110`).

## Suggested sequence

1. Preserve current release evidence and verify a restorable backup; keep live tasks running while reviewing.
2. Resolve D1/D2 and add migration contract tests; repair historical data only as a separately reviewed operation.
3. Resolve D3/D4 and add data-integrity/lifecycle tests.
4. Add release gates (D5), correct platform claims (D6), and validate R1/R2.
5. Complete a production-version staging upgrade, UI build and final-release race run before unconditional approval.
